Verificar y diagnosticar la red en un cliente Windows 11

Criterio de evaluación: RA2.d

Objetivo: comprobar que la configuración TCP/IP de Windows funciona: puerta de enlace, equipos de la red, Internet, resolución de nombres y acceso a servicios web. Y localizar el fallo cuando algo no va.

1. La escalera de diagnóstico en Windows

Se comprueba de dentro hacia fuera. El primer peldaño que falla indica dónde mirar.

# Pregunta Comando Si falla, revisa…
1¿Tengo IP y no es 169.254?ipconfig /all · Get-NetIPConfigurationConfiguración del adaptador, VirtualBox
2¿Funciona la pila TCP/IP?ping 127.0.0.1El sistema (muy raro)
3¿Llego a un vecino?ping 192.168.100.10IP, máscara, red interna, el otro equipo
4¿Llego a la puerta de enlace?route print -4 y ping a esa IPRuta por defecto, adaptador NAT
5¿Salgo a Internet?ping 8.8.8.8Puerta de enlace, router
6¿Resuelvo nombres?nslookup google.com · Resolve-DnsNameServidores DNS
7¿Responde el servicio?Test-NetConnection … -Port 80 · curl.exe -IServicio del servidor, puerto, cortafuegos

Idea clave: ping comprueba que el equipo responde; Test-NetConnection -Port y curl.exe comprueban que un servicio concreto responde.

2. Revisar la configuración aplicada

ipconfig /all
Get-NetIPConfiguration -InterfaceAlias "Ethernet 2"
Get-NetIPConfiguration -InterfaceAlias "Ethernet"

Get-NetIPConfiguration resume los cuatro datos de cada adaptador:

InterfaceAlias       : Ethernet 2
IPv4Address          : 192.168.100.51
IPv4DefaultGateway   :                      ← vacío: correcto en la red interna
DNSServer            : 8.8.8.8
                       8.8.4.4

En el adaptador «Ethernet» (NAT) verás IPv4DefaultGateway : 10.0.2.2 y el DNS 10.0.2.3 que da VirtualBox.

3. ping en Windows: leer la respuesta

C:\> ping 192.168.100.10
Respuesta desde 192.168.100.10: bytes=32 tiempo<1m TTL=64
...
Estadísticas de ping para 192.168.100.10:
    Paquetes: enviados = 4, recibidos = 4, perdidos = 0
    (0% perdidos),

Windows envía 4 paquetes y para. ping -n 10 envía 10; ping -t no para hasta Ctrl+C.

Mensaje Qué está pasando
Tiempo de espera agotado para esta solicitud.El paquete sale pero no vuelve: equipo apagado, cortafuegos del otro equipo o ruta equivocada.
Respuesta desde 192.168.100.51: Host de destino inaccesible.Contesta tu propio equipo: el destino está en tu red y nadie responde a esa IP. ¡Ojo! Aunque pone «recibidos = 4», el ping ha fallado.
PING: error en la transmisión. Error general.No hay ruta hacia ese destino (falta puerta de enlace o adaptador deshabilitado).
La solicitud de ping no pudo encontrar el host google.com.Fallo de DNS o nombre mal escrito.

4. La puerta de enlace: encontrarla y probarla

route print -4    # busca la fila 0.0.0.0  0.0.0.0  10.0.2.2
Get-NetRoute -DestinationPrefix 0.0.0.0/0       # lo mismo en PowerShell
ping 10.0.2.2
tracert -d 8.8.8.8    # por dónde pasan los paquetes

En el laboratorio la puerta de enlace es 10.0.2.2 (NAT). En la red interna no hay router, así que ping 192.168.100.1 no contesta: es lo esperado.

Find-NetRoute -RemoteIPAddress 192.168.100.10 indica por qué adaptador saldría un paquete hacia esa IP (equivale a ip route get de Linux).

5. Comprobar el DNS

C:\> nslookup google.com
Servidor:  dns.google
Address:  8.8.8.8

Respuesta no autoritativa:            ← normal: no responde el dueño del dominio
Nombre:  google.com
Addresses:  2a00:1450:...
          142.250.184.14
nslookup google.com 1.1.1.1    # preguntar a un DNS concreto
Resolve-DnsName google.com -Type A              # versión PowerShell
ipconfig /displaydns    # lo que hay en la caché DNS
ipconfig /flushdns    # vaciar la caché

Errores típicos: DNS request timed out (el DNS no contesta) y *** dns.google no encuentra googel.com: Non-existent domain (el nombre no existe).

Si nslookup google.com falla y nslookup google.com 1.1.1.1 funciona, el problema está en los DNS configurados en el adaptador.

6. Comprobar servicios: puertos y web

6.1 Test-NetConnection: ¿está abierto el puerto?

PS> Test-NetConnection 192.168.100.10 -Port 80

ComputerName     : 192.168.100.10
RemoteAddress    : 192.168.100.10
RemotePort       : 80
InterfaceAlias   : Ethernet 2          ← sale por la red interna: bien
SourceAddress    : 192.168.100.51
TcpTestSucceeded : True                ← el puerto responde

Si sale TcpTestSucceeded : False con un aviso TCP connect to … failed, mira PingSucceeded: si el ping va y el puerto no, el problema es el servicio o el cortafuegos del servidor, no la red.

Sin -Port hace un ping. Abreviado: tnc 192.168.100.10 -Port 80.

6.2 curl.exe: pedir una página web

Windows 11 trae curl de serie. Escríbelo siempre como curl.exe: en PowerShell, curl a secas es un alias de otro comando (Invoke-WebRequest) con otras opciones y otra salida.

curl.exe -I http://192.168.100.10          # solo la cabecera
curl.exe -I https://www.google.com
curl.exe -s -o NUL -w "%{http_code}" https://www.google.com   # solo el código
HTTP/1.1 200 OK
Server: Apache/2.4.58 (Ubuntu)

Alternativa en PowerShell: (Invoke-WebRequest http://192.168.100.10 -UseBasicParsing).StatusCode → 200.

Respuesta Significado

curl: (6) Could not resolve hostDNS: no se conoce la IP del nombre.
curl: (7) Failed to connect … Connection refused
(o Could not connect to server)		El equipo responde pero no hay servicio en ese puerto.
curl: (28) … Timed outNadie contesta: equipo inalcanzable o cortafuegos.

curl.exe http://srv-ubuntu fallará con Could not resolve host: es un nombre interno de la ferretería que ningún DNS de Internet conoce. Con la IP funciona. Para usar nombres internos hace falta el archivo hosts o un DNS propio, que se ve en el tema de resolución de nombres.

9. Comprueba lo que has aprendido

Intenta responder antes de abrir cada pregunta para ver la solución.

1. ¿Cuál es la puerta de enlace de la VM Windows y cómo la ves?
Solución: 10.0.2.2, en la fila 0.0.0.0 de route print -4 o en Get-NetIPConfiguration del adaptador Ethernet.
2. Un ping muestra «Host de destino inaccesible» y «perdidos = 0». ¿Ha funcionado?
Solución: No. Las respuestas las da tu propio equipo para avisar de que el destino no contesta.
3. ¿Por qué hay que escribir curl.exe y no curl en PowerShell?
Solución: Porque en PowerShell curl es un alias de Invoke-WebRequest, que no entiende las opciones de curl como -I.
4. Test-NetConnection 192.168.100.10 -Port 80 da PingSucceeded True y TcpTestSucceeded False. ¿Dónde está el fallo?
Solución: En el servidor: la red funciona, pero no hay servicio web en el puerto 80 o el cortafuegos lo bloquea.
5. ¿Qué comando de Windows equivale a ip route get?
Solución: Find-NetRoute -RemoteIPAddress <IP>.
6. curl.exe -I https://google.com devuelve 301. ¿Hay un problema de red?
Solución: No. Es una redirección: el servidor ha respondido.
