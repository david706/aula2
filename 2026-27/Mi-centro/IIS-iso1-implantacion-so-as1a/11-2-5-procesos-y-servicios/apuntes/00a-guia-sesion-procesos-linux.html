1. Qué es un proceso

Una receta y un cocinero. Un programa es la receta: un archivo en el disco que no hace nada. Un proceso es la receta cocinándose: está en marcha, ocupa memoria y CPU y tiene un número, un dueño y un padre.
  • PID: el número único del proceso.
  • PPID: el PID de su padre (quien lo lanzó).
  • Dueño: el usuario con cuyos permisos corre.

Todos cuelgan de uno: el árbol de procesos

PID 1  systemd
 └─ sshd (root)
     └─ sshd: ana@pts/0
         └─ bash          ← tu terminal
             └─ ps -ef    ← el comando que acabas de lanzar

La columna STAT: en qué estado está

LetraSignificado
RCorriendo (usando CPU)
SDurmiendo: espera algo. Es lo normal
TParado (pausado con una señal)
ZZombi: ha terminado pero su padre no lo ha «recogido»

Prioridad: nice

El valor nice va de -20 (máxima prioridad) a 19 (mínima). Ser «amable» (nice alto) es ceder CPU a los demás. Un usuario normal solo puede subir su nice; bajarlo es cosa de root.

Señales: cómo se le habla a un proceso

SeñalNúmeroQué hace
TERM15Pide que termine con elegancia (la que se envía por defecto)
KILL9Lo mata sin avisar. Último recurso
STOP19Lo pausa (STAT = T)
CONT18Lo reanuda
¿Por qué no usar siempre kill -9? (clic para ver la respuesta)
El proceso no se entera: no cierra archivos ni avisa a sus hijos y puede dejar datos corruptos. Primero se manda la 15 y solo si no responde, la 9.

2. Misión 1 · Fotografía del sistema

Mira el árbol de procesos: 
ps -ef --forest | head -40
Verás algo como: 
root     1     0 ... /sbin/init                 ← PID 1: systemd
root     2     0 ... [kthreadd]                ← kernel (entre corchetes)
root   812     1 ... sshd: /usr/sbin/sshd
ana   1532  1498 ... -bash                     ← tu shell
Averigua el PID de tu shell y el de su padre: 
echo $$
ps -o ppid= -p $$
Localiza el servicio SSH: 
pgrep -a sshd
Los procesos que más memoria usan: 
ps aux --sort=-%mem | head -6
Para la práctica: no basta con pegar la salida; hay que señalar el PID 1 y qué es, tres procesos del kernel, tu shell y su padre, y el PID de sshd.
¿Cómo reconoces un proceso del kernel? (clic para ver la respuesta)
Va entre corchetes (por ejemplo [kthreadd]) y su padre es el PID 2.

3. Misión 2 · El proceso que se come la CPU

Un usuario lanza algo que ocupa toda la CPU. Tú, como administrador, lo controlas sin matarlo a lo bruto.

Terminal A (como pedro). Lanza el proceso en segundo plano y anota su PID: 
sudo -u pedro bash
sha256sum /dev/zero &
echo $!
Deja la terminal A abierta: si cierras la sesión, el proceso puede morir.
Terminal B (administrador). Míralo en top (sal con q): debe ocupar ~100 % de CPU.
top
Localízalo por nombre y dueño y mira su prioridad: 
pgrep -u pedro sha256sum
ps -o pid,ni,stat,cmd -p PID
Sustituye PID por el número real. Salida: 
  PID  NI STAT CMD
 2210   0 R    sha256sum /dev/zero
Bájale la prioridad a nice 15 y comprueba que la columna NI cambia: 
sudo renice -n 15 -p PID
ps -o pid,ni,stat,cmd -p PID
Páralo y comprueba que STAT pasa a T; luego reanúdalo y STAT vuelve a R: 
sudo kill -STOP PID
ps -o pid,ni,stat,cmd -p PID
sudo kill -CONT PID
ps -o pid,ni,stat,cmd -p PID
Termínalo bien, con la señal por defecto (15), sin -9: 
sudo kill PID
ps -p PID
Ya no debe aparecer. En la terminal A verás Terminated.
Si renice da «Operation not permitted», ¿qué falta? (clic para ver la respuesta)
Falta sudo: solo root puede bajar el nice de un proceso de otro usuario.
Haces pgrep -u pedro sha256sum y no sale nada. ¿Por qué? (clic para ver la respuesta)
Lo más probable es que la terminal A se cerró y el proceso murió, o que lo lanzaste con otro usuario. Vuelve a lanzarlo y mantén abierta la terminal.

4. Qué es un servicio

Un servicio es un proceso que arranca solo con el sistema, vive en segundo plano y tiene un vigilante: si se cae, lo relanza. En Linux el vigilante es systemd (el PID 1), y se maneja con systemctl.

Dos preguntas distintas

PreguntaComandoRespuestas
¿Está corriendo ahora?systemctl is-active servicioactive / inactive
¿Arrancará al reiniciar?systemctl is-enabled servicioenabled / disabled
Ahora mismoAl reiniciar
start / stoplo arranca / lo parano cambia
enable / disableno cambiaarranca / no arranca

--now hace las dos cosas a la vez: enable --now y disable --now.

Un servicio está active y disabled. ¿Qué pasa al reiniciar el equipo? (clic para ver la respuesta)
No vuelve a arrancar: ahora corre, pero no está habilitado.

5. Misión 3 · start no es enable

Instala Apache y mira cómo queda: 
sudo apt install -y apache2
systemctl is-active apache2
systemctl is-enabled apache2
ss -tlnp | grep :80
En Ubuntu el paquete arranca y habilita el servicio solo: active, enabled y Apache escuchando en el 80.
Páralo sin deshabilitarlo y compara: 
sudo systemctl stop apache2
systemctl is-active apache2
systemctl is-enabled apache2
ss -tlnp | grep :80
Ahora es inactive pero sigue enabled, y el puerto 80 queda libre.
Deshabilítalo del todo y reinicia la VM: 
sudo systemctl disable --now apache2
systemctl is-enabled apache2
sudo reboot
Al volver: is-active → inactive y ss -tlnp | grep :80 vacío. Pega la salida de después del reinicio.
Ahora lo contrario: déjalo activo y habilitado y vuelve a reiniciar: 
sudo systemctl enable --now apache2
sudo reboot
Al volver, is-active → active y ss -tlnp | grep :80 muestra Apache escuchando.
Para ver el nombre del proceso en ss usa sudo ss -tlnp. Sin sudo, la columna del proceso sale vacía.
¿Cuáles son las 2 cosas que debes demostrar con reinicio? (clic para ver la respuesta)
Que con el servicio disabled no vuelve tras reiniciar, y que con enabled sí vuelve. Se documenta con is-active, is-enabled y ss en cada caso.

6. Misión 4 · Tu propio servicio (remate en casa)

Crea un servicio que cada 30 segundos escriba la fecha y el número de archivos de /srv/contabilidad en un log, que arranque con el sistema y que se relance solo si falla.

Escribe el script /usr/local/bin/monitor-conta.sh y hazlo ejecutable.
Crea la unidad /etc/systemd/system/monitor-conta.service con Restart=always y RestartSec=5.
Recarga systemd, habilítalo y arráncalo. Demuestra: status, el log creciendo, que al matar el proceso con kill -9 systemd lo relanza (PID nuevo) y que sigue activo tras un reinicio.
Pista

Un bucle infinito con sleep 30. La unidad tiene tres bloques: [Unit], [Service] y [Install]. Para ver el PID: systemctl show -p MainPID monitor-conta.

Solución completa (clic para ver la respuesta)
sudo tee /usr/local/bin/monitor-conta.sh >/dev/null <<'EOF'
#!/bin/bash
while true; do
  echo "$(date) $(ls /srv/contabilidad | wc -l) archivos" >> /var/log/monitor-conta.log
  sleep 30
done
EOF
sudo chmod +x /usr/local/bin/monitor-conta.sh

sudo tee /etc/systemd/system/monitor-conta.service >/dev/null <<'EOF'
[Unit]
Description=Monitor de la carpeta de contabilidad
After=network.target

[Service]
ExecStart=/usr/local/bin/monitor-conta.sh
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now monitor-conta
systemctl status monitor-conta
systemctl show -p MainPID monitor-conta
sudo kill -9 PID ; sleep 6
systemctl show -p MainPID monitor-conta     # PID nuevo
tail -3 /var/log/monitor-conta.log

Reflexión: ¿cuándo sería un problema Restart=always? (clic para ver la respuesta)
Si el servicio falla al arrancar por un error de configuración, entra en un bucle de reinicios que consume recursos y llena los logs. Hay que limitar los reintentos o usar Restart=on-failure.

Ideas clave

  1. Un proceso es un programa en marcha: se localiza con ps/pgrep, se prioriza con renice, se pausa con STOP y se termina con 15. El 9 es el último recurso.
  2. start no es enable: uno cambia el ahora y el otro el próximo arranque. Se comprueba reiniciando.
  3. Lo que no se usa se deshabilita: es una medida de seguridad, no solo de rendimiento.
  4. Una misión no está hecha hasta que está comprobada con la salida real.
