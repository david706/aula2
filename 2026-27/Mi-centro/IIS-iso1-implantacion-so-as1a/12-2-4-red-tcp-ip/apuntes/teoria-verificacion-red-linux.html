Verificar y diagnosticar la red en un cliente Linux

Criterio de evaluación: RA2.d

Objetivo: comprobar que la configuración TCP/IP del cliente funciona de verdad: que llega a la puerta de enlace, a los equipos de la red y a Internet, que resuelve nombres y que puede usar servicios como una web. Y, si algo falla, saber localizar dónde.

1. Configurar no es lo mismo que funcionar

Que el archivo de Netplan esté bien escrito no garantiza que el equipo tenga red. Puede fallar el cable (en VirtualBox, el adaptador), el otro equipo, el router, el DNS o el servicio al que queremos acceder. Por eso se comprueba por capas, de dentro hacia fuera. El primer peldaño que falla indica dónde está el problema.

# Pregunta Comando Si falla, revisa…
1¿Mi interfaz está activa y tiene IP?ip -br a · nmcli device showNetplan, adaptador en VirtualBox
2¿Funciona la pila TCP/IP?ping -c 2 127.0.0.1El sistema (muy raro que falle)
3¿Llego a un vecino de mi red?ping -c 4 192.168.100.10IP, máscara, red interna, el otro equipo
4¿Llego a la puerta de enlace?ip route y ping a esa IPRuta por defecto, adaptador NAT
5¿Salgo a Internet?ping -c 4 8.8.8.8Puerta de enlace, router, proveedor
6¿Resuelvo nombres?nslookup google.comServidores DNS
7¿Responde el servicio que quiero usar?curl -I http://192.168.100.10El servicio en el servidor, el puerto, el cortafuegos

Idea clave: ping comprueba que un equipo responde. curl comprueba que un servicio de ese equipo responde. Un servidor puede contestar al ping y tener la web apagada.

2. Revisar la configuración aplicada

2.1 Lo que pedimos y lo que el sistema tiene

El archivo de Netplan es lo que pedimos. Lo que el sistema tiene de verdad se ve con estos comandos. Si no coinciden, falta aplicar o hay un error.

sudo cat /etc/netplan/01-netcfg.yaml     # lo que pedimos
sudo netplan get                         # lo que Netplan entiende (todos los archivos unidos)
ip -br a                                 # lo que hay aplicado

2.2 nmcli device show: los cuatro datos de un vistazo

En Ubuntu Desktop la red la gestiona NetworkManager. Su herramienta de terminal, nmcli, enseña en un solo listado IP, máscara, puerta de enlace y DNS de cada interfaz:

nmcli device status          # resumen: interfaz, tipo, estado, conexión
nmcli device show enp0s8     # detalle de una interfaz
GENERAL.DEVICE:          enp0s8
GENERAL.TYPE:            ethernet
GENERAL.HWADDR:          08:00:27:xx:xx:xx        ← MAC
GENERAL.STATE:           100 (conectado)          ← 100 = funcionando
GENERAL.CONNECTION:      netplan-enp0s8           ← creada desde tu archivo Netplan
IP4.ADDRESS[1]:          192.168.100.50/24        ← IP + máscara
IP4.GATEWAY:             --                       ← sin puerta de enlace (correcto)
IP4.DNS[1]:              8.8.8.8
IP4.DNS[2]:              8.8.4.4

Si lo haces con enp0s3 (el NAT) verás IP4.GATEWAY: 10.0.2.2 y IP4.DNS[1]: 10.0.2.3: son la puerta de enlace y el DNS que VirtualBox entrega por DHCP.

El texto del estado sale en el idioma del sistema: «conectado» o «connected».

3. ping: leer bien la respuesta

ping envía paquetes ICMP de eco y espera respuesta. No usa puertos: comprueba solo que el equipo es alcanzable.

$ ping -c 4 192.168.100.10
64 bytes from 192.168.100.10: icmp_seq=1 ttl=64 time=0.48 ms
...
--- 192.168.100.10 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3050ms
  • ttl: «vida» del paquete; baja 1 en cada router. Con 64 sabemos que no ha pasado por ningún router (es un vecino Linux).
  • time: lo que tarda en ir y volver. En la red local, menos de 1 ms.
  • packet loss: el dato importante. 0% = bien. 100% = no hay respuesta.

3.1 Mensajes de error de ping y qué significan

Mensaje Qué está pasando
Destination Host UnreachableEl destino está en mi red pero nadie contesta a esa IP: equipo apagado, IP equivocada o red interna distinta en VirtualBox.
Network is unreachableNo tengo ninguna ruta hacia ese destino: falta la puerta de enlace o la interfaz está caída.
100% packet loss sin más mensajesEl paquete sale pero no vuelve: cortafuegos que bloquea ICMP, router que no reenvía, o el paquete sale por la interfaz equivocada.
Temporary failure in name resolution
Name or service not known		No se ha podido traducir el nombre a IP: problema de DNS (o nombre mal escrito). La red puede estar bien.

3.2 ¿Por qué interfaz sale un paquete?

Muy útil cuando un ping falla sin explicación:

$ ip route get 192.168.100.10
192.168.100.10 dev enp0s8 src 192.168.100.50     ← correcto: sale por la red interna
$ ip route get 8.8.8.8
8.8.8.8 via 10.0.2.2 dev enp0s3 src 10.0.2.15     ← correcto: sale por el NAT

Si 192.168.100.10 sale por enp0s3, tu IP o tu máscara de enp0s8 están mal: el sistema no cree que el servidor sea un vecino.

4. La puerta de enlace: encontrarla y probarla

No hace falta saberla de memoria: la tabla de rutas la dice.

$ ip route | grep default
default via 10.0.2.2 dev enp0s3 proto dhcp metric 100
$ ping -c 4 10.0.2.2

En nuestro laboratorio la puerta de enlace es 10.0.2.2 (el NAT de VirtualBox). La red interna 192.168.100.0/24 no tiene router, así que ping 192.168.100.1 no responderá, y es lo esperado. En una oficina real con un router en 192.168.100.1, sí sería ese.

Para ver por dónde pasan los paquetes hasta un destino de Internet:

tracepath -n 8.8.8.8          # viene instalado; traceroute hay que instalarlo

Detrás del NAT de VirtualBox es normal que muchos saltos aparezcan como no reply.

5. nslookup: comprobar el DNS

$ nslookup google.com
Server:         127.0.0.53            ← intermediario local (systemd-resolved)
Address:        127.0.0.53#53         ← #53 = puerto del DNS

Non-authoritative answer:            ← responde un DNS que no es el dueño del dominio: normal
Name:   google.com
Address: 142.250.184.14               ← la respuesta

5.1 Preguntar a un servidor DNS concreto

Si la resolución falla, pregunta directamente a un DNS público. Así separas «mi configuración DNS está mal» de «no hay salida a Internet»:

nslookup google.com 8.8.8.8      # pregunta a Google
nslookup google.com 1.1.1.1      # pregunta a Cloudflare
resolvectl dns                   # qué DNS usa cada interfaz
nslookup google.com nslookup google.com 8.8.8.8 Conclusión
RespondeRespondeTodo bien.
FallaRespondeLa salida funciona; los DNS configurados están mal.
FallaFalla (timed out)No hay salida a Internet: vuelve al peldaño 4 y 5.

Respuestas de error habituales: ;; connection timed out; no servers could be reached (el DNS no contesta) y ** server can't find googel.com: NXDOMAIN (el DNS contesta, pero ese nombre no existe: revisa cómo lo has escrito).

6. curl: comprobar que un servicio web responde

curl hace una petición a una URL igual que un navegador, pero desde la terminal. Usa TCP y un puerto: 80 para http:// y 443 para https://.

sudo apt install curl                    # Ubuntu Desktop no lo trae de serie
curl http://192.168.100.10               # descarga la página (sale el HTML entero)
curl -I http://192.168.100.10            # solo la cabecera de la respuesta
curl -I https://www.google.com
curl -sS -o /dev/null -w "%{http_code}\n" https://www.google.com   # solo el código

La primera línea de curl -I dice si el servidor ha atendido la petición:

HTTP/1.1 200 OK
Server: Apache/2.4.58 (Ubuntu)           ← qué servidor web contesta
Content-Type: text/html

6.1 Códigos de respuesta HTTP

Código Significado
200 OKTodo bien: el servicio funciona y ha entregado la página.
301 / 302Redirección a otra dirección (por ejemplo, de google.com a www.google.com). El servidor responde: la red funciona. Con curl -L sigue la redirección.
403Prohibido: el servidor responde pero no deja ver ese recurso (permisos).
404No encontrado: el servidor responde, pero esa página no existe.
500Error interno del servidor web.

Recuerda: cualquier código, aunque sea 404, demuestra que la red y el servicio funcionan. Los problemas de red se ven en los errores de curl:

6.2 Errores de curl y dónde está el fallo

Error Diagnóstico
curl: (6) Could not resolve host: srv-ubuntuDNS: no se sabe qué IP tiene ese nombre.
curl: (7) Failed to connect to 192.168.100.10 port 80 … Connection refusedLa red funciona (el servidor contesta), pero no hay ningún servicio escuchando en ese puerto: la web no está instalada o está parada.
curl: (28) Connection timed out / Failed to connect … TimeoutNadie contesta: equipo inalcanzable o cortafuegos que descarta los paquetes del puerto.
curl: (7) … No route to hostNo hay ruta o el cortafuegos rechaza activamente la conexión.
curl: (60) SSL certificate problemLa conexión llega, pero el certificado HTTPS no es de confianza (o la hora del equipo está mal).
orden no encontrada / command not foundNo está instalado: sudo apt install curl.

6.3 ¿Por qué curl http://srv-ubuntu no funciona?

Porque srv-ubuntu es un nombre que solo existe dentro de la ferretería: ningún DNS de Internet (como 8.8.8.8) lo conoce. Con la IP sí funciona: curl http://192.168.100.10. Para que el cliente traduzca nombres internos hace falta el archivo /etc/hosts o un servidor DNS propio, que se trabaja en el tema de resolución de nombres.

6.4 Sin curl: ¿está abierto el puerto?

nc -zv 192.168.100.10 80          # "succeeded" = puerto abierto; "refused" = sin servicio
wget -S --spider http://192.168.100.10   # alternativa a curl, viene instalada

7. En otras distribuciones

Los comandos de comprobación (ip, ping, nslookup, curl) son los mismos en todas. Cambia el paquete donde vienen y la herramienta que muestra la configuración:

Distribución Instalar curl y nslookup Ver la configuración aplicada
Ubuntu / Debiansudo apt install curl bind9-dnsutilsnmcli device show (Desktop) · networkctl status (Server)
Fedora / RHELsudo dnf install curl bind-utilsnmcli device show
Arch Linuxsudo pacman -S curl bindnetworkctl status o nmcli device show, según el gestor que hayas activado

En todas, resolvectl status muestra los DNS si se usa systemd-resolved.

9. Comprueba lo que has aprendido

Intenta responder antes de abrir cada pregunta para ver la solución.

1. ¿Qué diferencia hay entre comprobar con ping y con curl?
Solución: ping (ICMP) comprueba que el equipo es alcanzable. curl (TCP, puerto 80/443) comprueba que un servicio web de ese equipo responde.
2. ¿Por qué en nuestro laboratorio ping 192.168.100.1 no responde? ¿Cuál es la puerta de enlace?
Solución: En la red interna no hay ningún router. La puerta de enlace es la del NAT, 10.0.2.2, como muestra ip route.
3. En nmcli device show enp0s8 aparece IP4.GATEWAY: --. ¿Está bien?
Solución: Sí. La red interna no lleva puerta de enlace; la única está en enp0s3 (NAT).
4. nslookup google.com falla, pero nslookup google.com 8.8.8.8 funciona. ¿Qué concluyes?
Solución: Hay salida a Internet, pero los DNS configurados en el equipo están mal o no responden.
5. ping 192.168.100.10 funciona y curl http://192.168.100.10 da Connection refused. ¿Dónde está el problema?
Solución: En el servidor: la red funciona, pero no hay ningún servicio web escuchando en el puerto 80 (Apache no instalado o parado).
6. curl -I https://google.com devuelve HTTP/2 301. ¿Hay algún problema?
Solución: No. 301 es una redirección: el servidor ha respondido, así que red, DNS y servicio funcionan.
7. ¿Por qué curl http://srv-ubuntu da Could not resolve host y con la IP funciona?
Solución: Porque es un nombre interno que no conoce ningún DNS de Internet. Hace falta /etc/hosts o un DNS propio.
8. ¿Qué comando te dice por qué interfaz saldrá un paquete hacia una IP?
Solución: ip route get <IP>, por ejemplo ip route get 192.168.100.10.
9. ¿Cómo instalarías nslookup en Fedora y en Arch?
Solución: Fedora: sudo dnf install bind-utils. Arch: sudo pacman -S bind.
