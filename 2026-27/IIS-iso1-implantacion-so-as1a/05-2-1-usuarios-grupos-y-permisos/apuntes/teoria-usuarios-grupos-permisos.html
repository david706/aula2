1 · PUNTO DE PARTIDA

¿Por qué existen los usuarios?

Un sistema operativo multiusuario tiene que responder tres preguntas cada vez que alguien toca un archivo:

  1. ¿Quién eres? → identificación (usuario)
  2. ¿Puedes demostrarlo? → autenticación (contraseña)
  3. ¿Tienes derecho a hacer esto? → autorización (permisos)

Los grupos existen para no tener que dar permisos persona a persona: se da el permiso al grupo "contabilidad" y se mete o saca gente del grupo.

Principio de mínimo privilegio
Cada cuenta tiene exactamente los permisos que necesita para su trabajo. Ni uno más. Si una cuenta se ve comprometida, el daño queda acotado.
Regla de oro del administrador
Una persona = una cuenta. Nunca se comparten cuentas: sin trazabilidad no hay seguridad ni auditoría.
🤔 Pregunta a clase: ¿Por qué el instalador de Ubuntu no te deja entrar directamente como root? ¿Y por qué Windows te pide confirmación (UAC) aunque seas administrador?
Porque trabajar siempre con todos los privilegios convierte cualquier error o malware en un desastre total. Se trabaja como usuario normal y se eleva solo cuando hace falta (sudo / UAC).

2 · LINUX

Cómo guarda Linux a los usuarios

$ cat /etc/passwd
root:x:0:0:root:/root:/bin/bash
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
ana:x:1001:1001:Ana Pérez:/home/ana:/bin/bash
nombre : x : UID : GID : descripción : home : shell
  • UID = identificador numérico. Es lo que el sistema usa de verdad; el nombre es para humanos.
  • 0 = root · 1–999 = cuentas de servicio · ≥ 1000 = personas
  • La x indica que la contraseña está en otro archivo.
  • Shell nologin = cuenta que no puede iniciar sesión (servicios).
$ sudo cat /etc/shadow

3 · LINUX

Grupos: primario y secundarios

$ id ana
uid=1001(ana) gid=1001(ana) groups=1001(ana),27(sudo),1005(contabilidad)
$ getent group contabilidad
contabilidad:x:1005:ana,luis
  • Grupo primario (GID en /etc/passwd): el que reciben por defecto los archivos que creas. En Ubuntu es un grupo privado con tu nombre.
  • Grupos secundarios (/etc/group): tantos como haga falta. Aquí es donde se reparten los permisos.
  • Los cambios de grupo se aplican al iniciar sesión de nuevo (o con newgrp).

4 · LINUX

Comandos de gestión

# Crear
sudo adduser ana            # Ubuntu: interactivo, crea home, pide clave
sudo useradd -m -s /bin/bash luis   # bajo nivel, universal
sudo passwd luis
sudo groupadd contabilidad
# Modificar
sudo usermod -aG contabilidad ana   # añadir a grupo (-a = append)
sudo gpasswd -d ana contabilidad    # sacar del grupo
sudo usermod -L luis / -U luis      # bloquear / desbloquear
sudo usermod -s /usr/sbin/nologin luis
# Borrar
sudo deluser --remove-home luis
sudo groupdel contabilidad
# Contraseñas y caducidad
sudo chage -l ana           # ver
sudo chage -M 90 -W 7 ana   # máx 90 días, aviso 7 antes
sudo passwd -e ana          # forzar cambio en el próximo login
# Consultar
id ana ; groups ana
getent passwd ana ; getent group
who ; w ; last
El error que suspende exámenes
usermod -G sudo ana (sin -a) sustituye la lista de grupos secundarios: Ana sale de contabilidad. Siempre -aG.
5 · LINUX

root y sudo

  • root (UID 0) se salta todos los permisos. En Ubuntu su cuenta está bloqueada por defecto: nadie entra como root.
  • sudo ejecuta un comando con privilegios de root y lo registra en el log (/var/log/auth.log): sabemos quién hizo qué.
  • Quién puede usar sudo lo dice /etc/sudoers, que se edita solo con visudo (comprueba la sintaxis antes de guardar).
  • En Ubuntu basta con pertenecer al grupo sudo.
sudo -l                 # qué puedo hacer con sudo
sudo -i                 # shell de root (con cuidado)
sudo -u www-data ls /var/www   # actuar como otro usuario

Delegar solo lo necesario

Que el operador de backups pueda lanzar el script de copias, y nada más:

/etc/sudoers.d/backups
luis ALL=(root) NOPASSWD: /usr/local/bin/backup.sh

Esto es mínimo privilegio aplicado a la administración.

Comparación: sudo ≈ UAC + grupo Administradores en Windows. En ambos trabajas como usuario normal y elevas de forma puntual.
6 · PERMISOS LINUX

Leer ls -l

$ ls -l
-rw-r-----  1 ana  contabilidad  8192 oct  6 09:10 nominas.ods
drwxrwx---  2 ana  contabilidad  4096 oct  6 09:12 informes
-rwxr-x---  1 root sudo           312 oct  6 09:15 backup.sh
lrwxrwxrwx  1 root root             9 oct  6 09:16 actual -> informes
-rw-r-----

u · propietario

El usuario dueño del archivo (ana). Normalmente quien lo creó.

g · grupo

Los miembros del grupo del archivo (contabilidad), salvo el dueño.

o · otros

Todos los demás usuarios del sistema.

El primer carácter es el tipo: - archivo · d directorio · l enlace simbólico · c/b dispositivo.

Linux mira un solo trío. Si eres el dueño se aplica "u" y se acaba la comprobación, aunque "g" u "o" fueran más generosos. Si no eres el dueño pero estás en el grupo, "g". Si no, "o". root ignora todo.
7 · PERMISOS LINUX

r, w, x no significan lo mismo en un directorio

PermisoValorEn un ARCHIVOEn un DIRECTORIO
r read4Ver el contenido (cat, abrirlo)Listar los nombres que contiene (ls)
w write2Modificar el contenidoCrear, borrar y renombrar entradas dentro
x execute1Ejecutarlo como programa o scriptEntrar (cd) y acceder a lo que hay dentro

Caso 1 · r sin x (r--)

Puedes ver los nombres de los archivos pero no abrir ninguno ni entrar. Como un escaparate con la puerta cerrada.

Caso 2 · x sin r (--x)

Puedes entrar y abrir un archivo si sabes su nombre exacto, pero ls falla. Como un pasillo a oscuras: pasas si conoces el camino.

🤔 Creo /srv/publico con chmod 644 para que todos lean. Los usuarios ven la carpeta pero cd /srv/publico da "Permiso denegado". ¿Qué falta?
El permiso x. Para una carpeta de lectura pública hace falta 755 (r-x para grupo y otros). Regla práctica: a un directorio casi siempre se le da r y x juntos.

8 · PERMISOS LINUX

Octal, simbólico, chmod, chown, umask

Cada trío se suma: r=4, w=2, x=1.

rwxr-x--- = 750
OctalSimbólicoUso habitual
644rw-r--r--Archivo normal
755rwxr-xr-xScripts, directorios públicos
700rwx------Carpeta privada (~/.ssh)
600rw-------Claves, archivos con contraseñas
770rwxrwx---Carpeta de grupo cerrada al resto
777rwxrwxrwxCasi nunca es la respuesta correcta
# chmod — cambiar permisos
chmod 640 nominas.ods          # octal
chmod g+w nominas.ods          # simbólico: + añade
chmod o-rx informes/           #            - quita
chmod u=rwx,g=rx,o= backup.sh  #            = fija
chmod -R 750 /srv/proyecto     # recursivo
# chown / chgrp — cambiar dueño y grupo (root)
sudo chown ana:contabilidad nominas.ods
sudo chown -R ana /srv/proyecto
sudo chgrp contabilidad informes/
# umask — permisos por defecto al CREAR
umask            # 0022 → archivos 644, carpetas 755
umask 027        # archivos 640, carpetas 750
umask 077        # todo privado: 600 / 700
umask se resta del máximo: 666 para archivos (nunca nacen ejecutables), 777 para directorios. 666 − 022 = 644.
9 · PERMISOS LINUX

¿Quién puede borrar un archivo?

$ ls -ld /srv/buzon
drwxrwxrwx 2 root root 4096 /srv/buzon
$ ls -l /srv/buzon
-rw------- 1 ana ana 120 secreto.txt
🤔 Pedro no es ana ni root. ¿Puede leer secreto.txt? ¿Puede borrarlo?
Leer: no (600, cae en "otros"). Borrar: sí. Borrar o renombrar modifica la lista de entradas del directorio, y en el directorio Pedro tiene w y x. Los permisos del archivo protegen su contenido, no su existencia.
clic para mostrar respuesta
Idea clave
Crear, borrar y renombrar son operaciones sobre el directorio, no sobre el archivo. Por eso un 777 en una carpeta compartida es peligroso aunque los archivos estén protegidos.

La solución a este problema concreto es el sticky bit → siguiente diapositiva.

Esto también explica por qué /home/ana es 750 y no 777: nadie puede borrarle nada a Ana aunque algún archivo suyo sea legible.

Los tres bits especiales

BitOctalSe ve comoEfectoEjemplo real
SUID4xxx-rwsr-xr-xEl programa se ejecuta con los permisos del dueño del archivo, no de quien lo lanza/usr/bin/passwd (root): un usuario normal escribe en /etc/shadow
SGID2xxxdrwxrwsr-xEn directorios: lo que se crea dentro hereda el grupo del directorio. En ejecutables: corre con el grupo del archivoCarpeta compartida de departamento

chmod 2770 /srv/contabilidad   # SGID + rwxrwx---
chmod g+s  /srv/contabilidad   # igual, simbólico
chmod 1777 /srv/buzon          # sticky: buzón público
chmod +t   /srv/buzon
chmod u+s  programa            # SUID (muy raro necesitarlo)
find / -perm -4000 -type f 2>/dev/null   # auditar SUID
Receta "carpeta de departamento"
mkdir /srv/conta && chgrp contabilidad /srv/conta && chmod 2770 /srv/conta
Grupo correcto, cerrada al resto, y todo lo nuevo nace con grupo contabilidad. Para que además nazca con w para el grupo: umask 002 o una ACL por defecto.

Mayúscula S o T en ls -l = el bit está puesto pero falta la x debajo: normalmente un error.

11 · PERMISOS LINUX

ACL: cuando un solo grupo no basta

Un archivo solo tiene un dueño y un grupo. ¿Y si Marta (dirección) tiene que leer la carpeta de contabilidad sin poder escribir, y sin abrirla a "otros"?

Las listas de control de acceso añaden entradas para usuarios o grupos extra sin tocar u/g/o.

sudo apt install acl                 # suele venir ya
setfacl -m u:marta:rX /srv/conta     # usuario extra (X = x solo en dirs)
setfacl -R -m g:direccion:rX /srv/conta
setfacl -d -m g:contabilidad:rwx /srv/conta   # ACL POR DEFECTO: la heredan los nuevos
setfacl -x u:marta /srv/conta        # quitar
setfacl -b /srv/conta                # borrar todas
getfacl /srv/conta
$ ls -l
drwxrws---+ 2 ana contabilidad 4096 conta
$ getfacl conta
# owner: ana
# group: contabilidad
user::rwx
user:marta:r-x
group::rwx
mask::rwx
other::---
default:group:contabilidad:rwx
  • El + al final de los permisos avisa de que hay ACL.
  • mask = tope máximo para grupo y entradas extra.
  • Las ACL son el puente conceptual a Windows: allí todo son ACL.
12 · WINDOWS

Usuarios y grupos en Windows

  • Sin dominio, las cuentas son locales: viven en la base SAM del equipo (C:\Windows\System32\config\SAM, cifrada).
  • Cada cuenta y grupo tiene un SID: S-1-5-21-…-1001. Es el UID de Windows. Los permisos apuntan al SID, no al nombre.
  • Si borras "ana" y la vuelves a crear, tiene otro SID: para Windows es otra persona y pierde todos sus permisos (SID huérfano en las ACL).
  • Tipos de cuenta: local, cuenta Microsoft (vinculada a la nube) y, más adelante, de dominio (Active Directory, RA4).
whoami /user        # mi SID
whoami /groups      # mis grupos
wmic useraccount get name,sid

14 · WINDOWS

Permisos NTFS

Cada archivo o carpeta en NTFS tiene una ACL formada por entradas (ACE): quién (SID) + permitir/denegar + qué. Se ve en Propiedades → Seguridad.

Permiso NTFS≈ LinuxIncluye
Control totalrwx + chmod/chownTodo, incluso cambiar la ACL
ModificarrwxLeer, escribir, ejecutar, borrar
Lectura y ejecuciónr-xLeer y ejecutar / atravesar
Mostrar contenido de carpetar-x (solo dirs)Listar
Lecturar--Leer
Escritura-w-Crear y modificar, sin borrar

Regla 1 · Acumulación

Si estás en dos grupos, tienes la suma de sus permisos. Contabilidad (Modificar) + Becarios (Lectura) = Modificar. Diferencia clave con Linux, que solo mira un trío.

Regla 2 · Denegar gana

Un Denegar explícito anula cualquier Permitir, incluso Control total. Por eso casi nunca se usa: lo correcto es no conceder el permiso.

Regla 3 · Herencia

Subcarpetas y archivos heredan la ACL del padre (entradas en gris). Se puede deshabilitar la herencia: copiar las entradas o eliminarlas. Las entradas explícitas prevalecen sobre las heredadas.

15 · WINDOWS

Compartir en red e icacls

Al compartir una carpeta hay dos juegos de permisos:

  • Permisos de recurso compartido (pestaña Compartir): solo aplican al acceso por red. Tres niveles: Lectura, Cambiar, Control total.
  • Permisos NTFS (pestaña Seguridad): aplican siempre, en local y en red.
Permiso efectivo por red = el más restrictivo de los dos.
Compartido "Todos: Lectura" + NTFS "Modificar" → por red solo lectura.
Práctica estándar: compartido = Control total a Usuarios autenticados, y se controla todo con NTFS. Un solo sitio donde mirar.

Para comprobar qué puede hacer realmente alguien: Seguridad → Opciones avanzadas → Acceso efectivo.

icacls C:\Datos\Conta                       :: ver ACL
icacls C:\Datos\Conta /grant Contabilidad:(OI)(CI)M
icacls C:\Datos\Conta /grant marta:(OI)(CI)RX
icacls C:\Datos\Conta /remove Usuarios
icacls C:\Datos\Conta /inheritance:d        :: quitar herencia (copiando)
icacls C:\Datos\Conta /deny luis:(OI)(CI)W  :: evítalo
icacls C:\Datos\Conta /setowner ana /T
takeown /f C:\Datos\Viejo /r                :: tomar posesión
net share Conta=C:\Datos\Conta /grant:"Usuarios autenticados",FULL
net share                                   :: ver compartidos
F control total · M modificar · RX lectura+ejecución · R lectura · W escritura
(OI) hereda a archivos · (CI) hereda a subcarpetas · /T recursivo

icacls … /grant marta:(OI)(CI)RX ≡ setfacl -R -m u:marta:rX

PARA LLEVARSE A CASA

Las 7 ideas que hay que recordar

  1. Una persona, una cuenta. Los permisos se dan a grupos, no a personas.
  2. Mínimo privilegio: usuario normal + elevación puntual (sudo / UAC).
  3. El sistema identifica por UID / SID, no por nombre.
  4. En Linux solo cuenta un trío (u, g u o); en Windows los permisos se acumulan y Denegar gana.
  5. En un directorio, x es entrar y w es crear/borrar: borrar depende de la carpeta, no del archivo.
  6. SGID + umask/ACL por defecto para carpetas de equipo; sticky para buzones públicos.
  7. Por red, el permiso efectivo es el más restrictivo entre compartido y NTFS.
